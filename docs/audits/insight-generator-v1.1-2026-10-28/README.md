# Insight Generator V1.1：第一阶段审计

日期：2026-10-28。范围：现有实现、已保存真实调用、当前报告与展示层。**本阶段未修改生产代码、Schema 或 Prompt，未发起新模型调用，未改动用户会话或报告。** 新增文件仅为本目录审计文档、复现程序、冻结快照和检查结果。

## 结论

洞察信息量不足首先是现有生成契约和后处理的限制，不能归因为模型没有拿到销售结果，也不是多条合格洞察最终被截成一条。

1. Prompt 明确要求“每个任务最多一项，单任务只返回一条”；实际请求 Schema 又将上限设为 `min(3, 有证据的任务数)`。当前单任务销售分析的上限就是 **1**。
2. Prompt 优先 ranking/metric，difference 次之，并禁止自由文本复述数字、比较、名次、比例，示例倾向泛化的“该分组/切入点”。当前模型按此约束选择首位排名，输出通用建议。
3. 后处理只用 `primary_evidence_id` 生成 fact/finding。即使引用多个证据，也不会将排名、差额、合计组织为综合发现。
4. 原 Evidence Builder 没有为这个 Top N 结果构建相对领先比例、首尾比例或返回组内集中度。页面已有这些计算，但在报告保存后的独立展示层，未进入 LLM 输入。
5. 正则校验禁止的范围过宽，存在合法比较/推断边界被拒绝；同时无法可靠识别所有无依据业务断言。增加条数或直接放宽正则均不能解决可靠性问题。
6. 标题、摘要框架属于规则生成，不是模型输出；业务页面现在另有规则视图，需要分别评估 LLM 洞察、保存的 AnalysisReport 和最终显示内容。

## 二、哪些证据和上下文进入 LLM

实际输入结构为 `analysis_goal / goal_coverage / tasks / evidence / limitations`。

- 任务按 P0/P1/P2 排序；每任务存在业务证据时排除 coverage，取前 **20** 条；最后取全局前 **80** 条。
- 当前 7 条全部进入，差额和合计没有因截断丢失。排除 E0001 是显式选择策略，样本量仍保存在原报告。
- 排序基本依赖任务优先级与证据生成次序，未按用户目标相关性、信息增量、重复程度评分；极值可能与排名重复占用预算。
- 原始 user_query、Intent.constraints、批准筛选值/完整操作参数、字段元信息没有作为独立字段进入请求。部分范围通过 business_question 保留下来，本例确实包含 2026、华东、已完成、按城市、降序、Top 3，**不能说本例完全丢失了范围**。
- 原始问题与 approved_scope 在调用后进入 report.execution_metadata。批准后的 constraints 不再作为“尚需确认”的 limitations 传入。因此，未在 analysis_goal/business_question 中体现的禁止性边界存在传递不完整风险。
- 未向模型发送完整原始数据集；有每次 160 KiB 输入上限。证据的 scope/operation 名称较抽象，无法代替具体条件上下文。

[本例完整实际输入](02-actual-llm-input.json)，可直接检查所有 7 条证据。定位：[AnalysisReportService](../../../backend/app/services/analysis_report.py)，选择约在 90–99 行，元信息约在 151–155 行。

## 三、实际 Prompt 与 Schema

[完整现有 Prompt](current-prompt.txt)；[完整实际请求 Schema](actual-response-schema.json)。本次仅冻结，没有优化版本或新旧对比可交付。

关键原文：

> 不要自己写 fact/finding 或总结；这些客观事实由代码从主要证据生成。

> 每个任务最多选择一项有业务意义的重点，单任务只返回一条；……优先选择 ranking / metric，其次 difference。

> implication/recommendation/limitations 仅写定性、谨慎且有依据的解释，不能包含任何阿拉伯数字、中文统计数字、排名、比例、最高最低、显著性或已完成目标的声明。

其他限制进一步禁止“前两个”“三个”“前列”“排名”等数量指代或比较表达，并要求改写成短例的简洁表达。它减少了一部分数值幻觉，但同时削弱了比较洞察和建议的具体性。

数量上限不是一个位置：

| 层 | 限制 |
| --- | --- |
| 本地 InsightDraft | 1–8 条 |
| 实际 LLM 请求 Schema | 最多 min(3, 任务数)；本例 1 条 |
| Prompt | 每任务最多 1 条，单任务只返回 1 条 |
| 后处理 | 不截断 insights 列表；每主证据不得重复；任一非法条目导致整个生成失败 |
| 摘要 | 只拼接前 2 条 finding，最多 1200 字符；summary refs 取前 3 条洞察 |
| KPI | 最多 6 张；不是洞察数量限制 |

上述请求上限与本地校验上限不完全一致：materialize 不再次检查“每任务一条/全局三条”，因此不能将 Prompt 的要求视为本地强制约束；本例通过实际请求与原始返回确认是 1 条。

定位：[Prompt 与 request_schema](../../../backend/app/reporting/prompt.py)，约 6–26、48 行；[DraftInsight / Insight](../../../backend/app/domain/analysis_report.py)。

## 五、后处理、去重与最终保存

`materialize` 依次检查：

1. refs 存在、不重复、含主证据。
2. finding_type 与主证据类型兼容；主证据不得重复使用。
3. 单条引用不得跨任务。
4. implication/recommendation/limitations 的数值、统计断言、部分因果/利润断言正则；有有限否定警示例外。
5. 如有 P0 证据，至少存在一条 P0 洞察。**不是逐个 P0 都要求覆盖**。
6. fact 从主证据固定格式生成，finding 直接复制主证据 statement；加“可能意味着/可考虑”前缀及固定局限；按任务优先级与 insight_id 排序。

没有语义重复检测、信息价值评分、比较结论合并或候选优选。去重只限制相同 primary ID；排名和极值即使语义重复，主 ID 不同仍不一定被去重。

当前生成并保存：

| 字段 | 实际内容 |
| --- | --- |
| fact | 济南的已计算指标值为 21,250。 |
| finding | 在当前返回结果中，济南的销售额 · 合计为 21,250，并列值采用同一名次，排名 1。 |
| implication | “可能意味着：” + 模型原文 |
| recommendation | “可考虑：” + 模型原文 |
| evidence_refs | E0002 |

所以 fact 文案确实过于技术化；但完整 finding **包含销售额与排名**，并不是保存报告完全没有名次。

[后处理重放](04-materialized-insights.json)与[原保存 AnalysisReport](05-saved-analysis-report.json)逐字段一致。受控实验仅把 refs 扩充为 E0002/E0003/E0007/E0008，fact/finding 仍完全相同，证实多证据不会被自动综合。

摘要标题由 coverage 的固定映射决定，例如“计划内核心任务已有可用结果”；overview 是业务目标 + 任务数量 + 前两条 finding，不由 LLM 写 executive summary。技术化标题的根因因此也不只是 Prompt。

定位：[事实生成与校验](../../../backend/app/reporting/fact_validation.py)，约 29–78 行；[报告组装](../../../backend/app/services/analysis_report.py)，约 125–165 行。

## 七、建议生成与失败处理

**保存报告：** recommendation 来自真实 LLM，代码加前缀并复制为 report.recommendations。固定提示/警示与摘要外壳来自规则。

**当前特定排名展示页：** 建议由规则根据可用字段构造，未采用原 LLM 建议；一般视图仍展示原建议。它是成功报告的常规展示分支，不是失败兜底。

**真实 LLM 失败：** 服务抛出超时、连接、JSON/Schema、引用或事实校验错误；ReportWorkflow 保存报告失败状态，保留真实 Engine 执行结果。不会用模板或 Mock 伪造成功。无有效证据时不调用 LLM，报告显式 unavailable，不生成洞察。项目仍有旧 MockReportModule，仅用于旧 Mock 路径，真实路径拒绝 mock provenance。

**重试：** 单次报告生成只有一次 Provider 调用，无自动多轮修复或反思；失败后可显式重试报告。现有报告状态记录以当前尝试为主，不是不可变的完整尝试档案；此次保存的专项真实调用日志补足了审计链路，生产通用追踪能力仍应单独评估。

定位：[真实报告 Workflow](../../../backend/app/workflow/reporting.py)、[Provider](../../../backend/app/llm/compatible_provider.py)。

## 八、事实安全校验的实际局限

本次以已保存真实证据为输入构造隔离草案进行诊断，没有提交 LLM、没有保存为用户报告：

| 受控草案 | 当前校验 | 判断 |
| --- | --- | --- |
| 济南与南京相差1000，值得进一步核查。 | 拒绝 | 差额在引用证据中仍因自由文本含数字而拒绝 |
| 济南利润高于南京，可以增加投入。 | 通过 | 无利润证据，表述漏检 |
| 济南销售额源自当地促销补贴。 | 通过 | 无促销证据，原因断言漏检 |
| The profit share is ninety percent. | 通过 | 英文比例断言漏检 |
| 销售额不能证明盈利能力。 | 拒绝 | 合理推断边界误拦截 |

[受控实验完整结果](controlled-probes.json)。这是校验缺口的复现，**不是模型实际输出或模型错误率**。不能把“所有可识别关键事实严格校验”作为现状承诺；当前 report.fact_validation 也明确只标记结构化事实已验证、解释未严格验证。

## 十、建议的最小后续方案（尚未实施）

1. **先冻结评测再调优。** 保留本目录基线；固定销售、招聘、客服、项目运营和独立未见案例；让各版本使用同一完整输入，分别存原始返回、最终报告与页面展示，不能混评。
2. **补充目标相关证据组织。** 重用确定性计算，优先提供排名—差额—返回范围集中度的证据组合，避免重复极值挤占预算。比例必须先生成可追踪 Evidence，明确“返回组内”分母；不能直接把 V 证据字符串塞进结论当作原有事实。
3. **补全输入范围。** 有界传递原始目标、已批准约束和必要字段名称/类型，保持禁止边界，不发送完整数据集。
4. **解除按任务数限制的信息瓶颈。** 在总量 1–3 条的指导下按证据信息量决定，不要求单任务必定多条，也不靠凑数；优先级从单排名调整为与目标相关的比较价值。
5. **解决多证据事实表达。** 复用现有 Insight 的 fact/finding/implication/recommendation/refs 字段。优先用可验证的证据组合生成事实，模型负责选择和谨慎解释；不能仅新增引用却仍只渲染 primary。若确需最小内部草案契约调整，应另行说明兼容性，而不是改下游公开 Schema。
6. **校验与建议质量同步优化。** 校验合法实体、数值、名次、分母和来源范围，再处理未验证解释；不以直接删除数字正则代替事实验证。建议必须指向某条发现及可验证的后续分析；没有成本/利润证据不引导已证实的盈利或效率结论。
