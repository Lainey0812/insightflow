# InsightFlow：城市集合约束与审批审计一致性修复

## 一、任务目标

修复 RF-01、RF-03 中城市范围约束无法被审批审计正确验证的问题，使合法计划能够通过现有 HITL 审批流程。

本轮只处理：

- Intent Parser 的城市范围约束表达。
- 用户约束与计划条件之间的语义匹配。
- 审批审计中由上述问题引起的误判。

不修改 Planner 业务逻辑、Analysis Engine、Golden Set、Oracle 或审批安全规则。

## 二、先审查现有实现

修改代码之前，请先定位并报告：

1. Intent Parser 如何提取用户的城市范围。
2. `filters`、`business_goal`、`metric_requirements` 如何进入约束审计。
3. 审计如何比较 `eq`、`in` 等操作符。
4. `all_verified` 如何影响 `can_approve`。
5. RF-02 为什么能通过，而 RF-01、RF-03 不能。

请提供具体文件路径、函数名称和关键逻辑。

## 三、目标行为

对于：

「对比上海和深圳的岗位数量，排除实习岗位」

系统应当能够证明：

- 城市范围为上海、深圳。
- 岗位类型排除实习。
- 分析指标为岗位数量。
- 计划中的过滤和聚合操作均有用户需求依据。

对于：

「只统计实习岗位，再对比上海和深圳」

系统应当能够证明：

- 城市范围为上海、深圳。
- 岗位类型仅包含实习。
- 分析指标为岗位数量。

## 四、修复约束

1. 优先采用确定性的语义规范化，不允许仅凭自然语言相似度放行。
2. 集合比较必须考虑字段、操作符、集合元素和逻辑关系。
3. 不得将 `A AND B` 无条件视为 `A IN [A,B]`。
4. 不得允许计划增加用户没有授权的过滤条件。
5. 保留约束与用户原始表达之间的来源关系。
6. 不得通过删除城市筛选、跳过审计或强制设置 `all_verified=true` 解决问题。
7. 如果需要调整数据契约，先评估兼容性，优先最小修改。

## 五、回归验证

使用现有固定的 9 行合成数据和 RF-01 至 RF-05。

重点验证：

- RF-01：上海 3、深圳 1。
- RF-02：上海 4、深圳 3。
- RF-03：上海 1、深圳 2。
- RF-05：深圳 3、北京 1、杭州 1。

RF-04 暂不作为本轮修复目标。

同时补充负向测试：未经用户授权的城市、额外过滤条件、错误集合运算不得通过审批。

## 六、实施方式

采用两阶段：

**阶段 A：审查与方案**

先输出根因、最小修改点、兼容性风险和测试方案，不修改代码。

**阶段 B：实施与验证**

待我确认阶段 A 后，再修改代码并执行回归测试。

禁止修改历史评测记录或通过修改 Oracle 提高通过率。

## 七、交付内容

请输出：

1. 根因及证据。
2. 推荐修复方案。
3. 涉及文件及修改范围。
4. 可能影响的其他业务场景。
5. 正向与负向回归测试清单。
6. 是否需要调整现有约束 Schema。

本轮先执行阶段 A，不要直接实施。
