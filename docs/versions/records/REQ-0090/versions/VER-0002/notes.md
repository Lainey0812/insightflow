# 审批约束映射与报告交付可靠性修复

需求：REQ-0090（用户确认先修审批，再修报告交付）。日期：2026-11-04。

**结论：审批可达性明显改善，报告交付增加；报告业务质量仍未通过验收，不建议扩大用户试用。** 这不是新的完整 MVP 发布。尤其不能把系统 report_status=complete 当作业务质量已经通过。

## 改动范围

### 审批约束证明

新增 `backend/app/review/bindings.py`，复用现有 ConstraintAuditor，不增加 LLM 或新的审批状态机。

- 通过真实字段元信息识别有限的订单、岗位、工单、任务记录计数表达，绑定 `count(field=null)`。它表示上传数据行，不表示去重后的现实实体总量。源文件出现同名数量字段时不擅自将其解释为行数。
- 区分行计数、非空计数、去重数和数值求和；错误函数不能沿用计数证明。
- 从完整、未截断的类别样本唯一绑定“只看一组和二组”等明确范围，证明实际 `in` / `not_in` 条件；集合比较不依赖顺序。歧义、未知值与多字段同值继续阻断。
- 支持明确排除、“不排除北京”、排序与 Top N 的组合、真实日期字段派生月份/年份后的排序。
- 对业务目标中明确的字段分组也建立操作证明；重复字段名保持 ambiguous，不按列表顺序选字段。
- 仍拒绝未经提及的额外筛选、提前截取、错误维度、多次汇总、错方向、错 Top N 及跨任务拼接条件。

审计副契约升级 2.1，保留 2.0 的解析兼容；原 Approval、PlanVersion、Execution、Session 状态权威不变。旧不可变审计载荷不回写。既有界面仍展示“拟用统计口径：记录数”，技术证明额外记录 `uploaded_rows_not_distinct_entities`，不静默改为 distinct_count。

原 9 个审批阻塞计划的**相同已保存输入**重新证明：8 个得到实际步骤证明，T04 的缺字段利润禁止/自由因果边界仍无法形成可靠证明，继续阻断。详见 saved-plan-proof-revalidation.json。此结果不是重新生成计划碰巧变好的替代指标。

### 报告交付

- 增加实际 P0 指标组清单，要求先覆盖核心组再选择辅助发现；动态 Schema 条数下限与核心组数一致。超过八个核心组明确返回范围错误，不静默丢掉核心要求。
- limitations 从程序构建的已验证完整句子中选择；自由模型文本仍不能补算缺失数。公开 AnalysisReport / Insight 字段保持不变。
- 缺少主证据引用时，仅在真实 ID、同任务/结果/指标/范围、来源和计算均验证后，补入模型已经明确选择的 primary ID。原始草稿不修改，修复记录保存到 metadata/Event；非法或跨范围引用仍拒绝。实际新模型回归中该修复次数为 0，不能把它宣称为交付改善的实测原因。
- 对封闭的否定性原因边界进行验证视图归一化；肯定性续句、利润断言、数字和未定义强度继续校验。没有直接删除数字正则、静默删掉不安全正文或生成规则洞察兜底。
- KPI 改为“最高值/高出幅度”，避免将较高响应时长默认描述成经营领先。
- 图表尊重批准操作链已有排序，存在 sort/top_n 时按真实结果顺序显示，不以默认降序覆盖用户升序要求。
- 历史 v1.1、v1.1.1、v1.2.0、v1.2.1 报告保持从已保存洞察读取，不因升级掉回另一套规则发现。不改写旧报告。

## 独立组与补跑

U组为已见回归，4例：系统报告 complete 2 / partial 1 / failed 1；执行者审阅 complete 2 / failed 2，其中升序图表错误保留为当次失败。

V组为最终主要回归的独立组，4例：系统报告 complete 2 / partial 1 / failed 1；4例计算均与独立 Pandas 一致。审阅为 complete 1 / partial 1 / failed 2：

- V01：系统报告 complete，但当时图表默认降序覆盖了升序要求，按冻结规则判 failed。
- V02：报告 partial，剩余解释含处理模式等待验证推测，不能认定充分业务验证。
- V03：多项目范围与计数正确，报告 complete。
- V04：均值计算正确，但否定原因边界表达仍被拦截，未交付。

随后只做确定性图表顺序修复。displayfix01 的 V01 真实链路保存 report_status=partial、ChartSpec.order=original，实际聚合值保持升序。详见 displayfix-validation.json。该补跑没有覆盖 V组旧输出，也没有改变其原始失败结论。

## 尚未解决的问题

1. **高风险：自由解释漏检。** repair02/S03 保存的解释出现“受产品结构和促销策略影响较大”“高频品类可能具有更强的用户粘性”。没有促销或复购证据，不能仅凭“待验证”前缀视为充分安全。这是 A–G 中 G=0，禁止以交付率掩盖。基线此例没有交付报告，当前保存了不安全解释，因此业务安全结果发生退化；不能因底层规则没有主动放宽就否认这项退化。当前版本不应作为业务验收通过版发布。
2. **误拦截仍存在。** T01 的未来核查建议、P04 的“由于仅包含均值…”、V04 的“目前数据不足以判断造成差异…”仍被拒绝。不能继续无限增加原句特例，后续应收紧事实/解释/建议的内部职责与结构化验证边界。
3. **领域相关性不足。** T02 客服建议套用“记录金额、销售差额”；P03 工时分析出现“单条记录金额”。没有捏造计算值，但降低业务可用性。
4. **审批有限语法仍有边界。** T04 无对应字段的利润禁令和报告因果边界没有完整证明；保持阻断。记录计数不解决数据真实粒度、去重实体数或岗位招聘人数语义。
5. **Planner 仍可能生成错误筛选值。** repair01/S01 将“华东”写成“华东地区”。独立基准与审批审计均拒绝该计划，未执行。保留实际失败，不改写为成功。
6. **可读性仍需优化。** 部分比例和均值小数过长，月份以数字显示；这些没有在本轮靠额外数值计算或模板结论掩盖。

因此，审批侧常见阻塞修复可评审；报告侧只能认定有改善，不能通过业务语义可靠性验收。下一步优先解决自由解释的无依据断言，再处理误拦截与领域适配。暂不扩大用户试用或开发新的后台功能。
