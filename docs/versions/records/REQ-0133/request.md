# 任务：完善 InsightFlow Admin 的 Intent Parser 节点详情

## 任务目标

基于现有 InsightFlow 项目，检查并完善 Intent Parser（需求理解）节点的运行可观测信息。

保留 Admin 现有左右布局：左侧完整 Workflow 节点流程，右侧展示当前选中节点的详情。

Intent Parser 是 LLM 节点，右侧采用三个 Tab：

1. Input：节点实际接收的输入。
2. Output：节点产生的结构化需求理解结果。
3. LLM：节点关联的真实模型调用信息。

不新增独立 Diagnostics Tab。节点状态、耗时和错误信息放在右侧顶部；质量问题主要通过 Input 与 Output 的对照发现。

## 第一阶段：检查现有实现

请先检查 Intent Parser 的真实执行代码、输入输出 Schema、Prompt 模板、LLM 调用记录、持久化机制及 Admin 现有节点详情组件。

列出所有实际字段，区分已存在且已展示、已存在但未展示、运行时存在但未持久化、完全缺失和不适用。

优先复用现有字段、接口和组件，不得凭需求描述假设字段已经存在。

## 第二阶段：Input Tab

检查并展示节点实际接收到的：

- 用户原始需求文本。
- 本轮补充说明或历史上下文（如果实际传入）。
- Dataset ID。
- 数据画像摘要，包括实际传入的字段名称、字段类型和质量信息。
- 已有的用户约束及其他上游上下文（如果存在）。

用户需求应作为主要信息展示。

数据画像采用简洁摘要，不重复 Data Profiler 的完整详情。

支持查看实际保存的结构化 Input JSON。

## 第三阶段：Output Tab

根据 Intent Parser 当前真实输出 Schema，设计业务化展示。

优先展示以下信息：

**分析目标：** 分析对象、业务目标、分析模式、维度和指标（以实际输出字段为准）。

**约束条件：** 模型识别出的显式约束、排除条件、时间范围、筛选条件及其他限制。尽可能展示约束来源、操作符和取值。

**澄清信息：** 是否需要澄清、缺失的关键条件、阻断原因和澄清问题（如果实际存在）。

**结构化结果：** 支持展开查看真实 Output JSON。

对于用户没有明确提出、但模型推断出来的条件，如果现有 Schema 支持来源标记，需要明确区分。不要将模型推断伪装成用户明确要求。

不要由 Admin 前端自行生成新的分析目标、约束或澄清结论。

不要求本次新增独立的约束遗漏检测算法。

## 第四阶段：LLM Tab

展示关联的实际 LLM Call：

- Call ID。
- 模型名称。
- Prompt 模板及版本。
- 调用状态、时间、延迟。
- 实际记录的 Token 使用量。
- 实际模型参数。
- 已保留的请求消息。
- 已保留的原始响应。
- 解析错误或调用错误（如果存在）。

支持一个 Node Run 关联多个 LLM Call，包括重试情况。

支持跳转 Prompt 管理模块查看对应版本。

未保留或过期的请求响应明确显示不可用，不重新生成历史数据。

## 第五阶段：前端交互

保留左侧 Workflow 节点列表。

点击 Intent Parser 时，右侧展示节点名称、执行状态、耗时及 Input / Output / LLM 三个 Tab。

默认展示 Output Tab。

Input 中重点突出用户原始需求，Output 中重点突出分析目标、用户约束和澄清信息，方便管理员人工对照判断模型是否遗漏或误解需求。

LLM Tab 用于进一步追溯 Prompt、模型配置及真实请求响应。

三个 Tab 切换不得重新执行节点。

若节点执行失败且无有效 Output，顶部展示错误信息，默认打开有实际记录的 Input 或 LLM 信息。

## 第六阶段：数据补齐规则

如果字段已经存在但未展示，直接复用。

如果执行时已经产生但没有持久化，补充必要的运行快照或引用。

如果字段完全不存在，先判断是否属于现有业务契约的必要信息，不要仅为了 Admin 展示而重构 Intent Parser。

尤其不要擅自修改 Intent Parser 的输出 Schema，因为下游 Analysis Planner 可能依赖该契约。

如果需要新增可观测字段，优先采用独立的 Trace 元数据，避免破坏业务输入输出结构。

历史运行缺失的信息显示「未采集」，不能通过当前 Prompt 或重新调用 LLM 补写历史。

## 第七阶段：验收

使用真实 Workflow 或明确标记的测试运行验证：

1. 能查看实际输入的用户需求及数据上下文。
2. 能查看结构化分析目标、约束和澄清结果。
3. 能查看关联的真实 LLM Call 和 Prompt 版本。
4. 能正确处理多次调用、失败调用和过期响应。
5. 能从 Input 与 Output 对照检查模型的需求理解结果。
6. 不影响下游 Planner 的现有输入契约。
7. 不改变 Admin 的左右布局。

完成后输出字段检查清单、实际修改内容、测试结果、未实现字段和兼容性风险。

请先检查代码，再按照最小改动原则实施。
