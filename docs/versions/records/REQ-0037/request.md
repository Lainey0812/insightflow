# InsightFlow — Insight Generator V1.1 第二阶段实施任务

## 一、任务目标

根据 2026-10-28 第一阶段审计结果，修复 Insight Generator 当前的结构性质量瓶颈。

本轮目标：

**让 Insight Generator 能够利用多个已验证证据，生成具有比较价值、业务意义且可追溯的洞察，并将其统一保存到 AnalysisReport。**

不以增加文字数量或洞察条数作为成功标准。

## 二、实施顺序

### Step 1：先建立冻结评测基线

在修改 Prompt 或生成逻辑之前：

- 冻结销售、招聘、客服、项目运营四类测试。
- 包含单任务、多任务、Top N、时间变化、缺失数据和不支持的业务解释。
- 建立独立未见测试集。
- 固定 A–G 七个评测维度。
- A 事实准确性、G 安全边界设置硬失败。
- 保存输入、原始 LLM 输出、AnalysisReport 和 Presentation 三层结果。

不能根据优化后的结果临时放宽评分规则。

### Step 2：增强 Evidence Builder

复用现有证据计算能力，增加必要的可验证比较证据。

针对销售订单案例，应能提供：

- 济南领先南京 1,000。
- 济南相对南京领先约 4.9%。
- 上海销售额约为济南的 27.1%。
- 济南和南京合计占返回前三名销售额的约 87.8%。

每条证据必须包含：

- evidence_id。
- 来源任务和结果。
- 参与计算的字段。
- 计算口径。
- 分子、分母或其他计算来源。
- 适用范围。

严格区分“返回 Top 3 内占比”和“全部华东地区占比”。

不要无限生成两两比较；优先根据用户目标和信息价值选择证据。

### Step 3：修改 Insight Generator 的生成契约

取消“每任务最多一条”的硬性限制。

整体建议 1–3 条高价值洞察，但根据证据信息量决定，不强制凑数。

允许 LLM 选择多个相关证据，组织成同一条综合发现。

例如：

“济南销售额排名第一，但仅领先南京约 4.9%；两座城市在当前统计范围内表现接近。”

以上数值必须来自 Evidence Builder。

Prompt 应要求：

- 优先回答用户核心分析目标。
- 优先选择信息增量高的比较或结构性发现。
- 避免重复排名和极值事实。
- 区分已验证事实、业务解释和待验证假设。
- 建议必须对应具体发现。
- 不生成无证据支持的因果、利润、成本或经营判断。

### Step 4：修复多证据事实生成

当前 materialize 仅使用 primary_evidence_id 生成 fact/finding，必须调整。

允许一条洞察关联多个有效证据。

优先由确定性代码根据受控证据组合生成可验证的事实表达。

LLM 负责选择证据组合、组织解释和提出建议。

如需调整内部 Draft Schema，先说明最小变更和兼容性。

尽量保持公开 AnalysisReport Schema 不变。

不能只增加 evidence_refs，而最终仍然只展示主证据。

### Step 5：改进事实校验

不能简单删除现有数字正则。

需要分别验证：

1. 证据 ID 是否存在。
2. 引用是否属于合法任务和统计范围。
3. 数值及计算口径是否来自真实证据。
4. 比较对象是否一致。
5. Top N 是否被误当成完整总体。
6. 解释中是否出现无依据的业务断言。
7. 建议是否被错误表述为已经验证的结论。

对于无法确定真假的自由文本解释，应采取保守策略：标记为待验证假设、要求改写，或拒绝进入报告。

不得宣称仅靠正则已实现完整语义事实验证。

### Step 6：统一保存报告与展示层

当前 Report Presentation 会独立生成 V001–V005 证据及三条规则发现。

本轮应将有价值的确定性比较证据前移到 Evidence Builder，并由统一的 Insight Generator 流程选择使用。

最终：

- AnalysisReport 是业务洞察的权威来源。
- Presentation 负责展示，不再独立创造另一套业务结论。
- HTML 导出和页面预览应使用一致的洞察来源。
- 图表、KPI 和格式化可以继续由确定性代码生成。
- 历史报告必须保持兼容；必要时采用明确的旧版展示逻辑，不静默改变原有保存内容。

### Step 7：真实 LLM 评测

沿用 qwen3.8-flash 和现有 Provider。

使用相同输入比较优化前后结果，并对独立未见案例进行测试。

分别评测：

- LLM 原始候选。
- 最终保存的 AnalysisReport。
- 用户实际看到的 Presentation。

不能混合三层结果计算同一个质量分数。

重点报告：

- 事实准确性。
- 重要证据利用率。
- 多证据综合能力。
- 业务目标相关性。
- 建议关联性。
- 用户可读性。
- 无依据断言和错误总体推断。

所有失败案例必须保留，不得只展示优秀案例。

## 三、开发边界

- 保持单 LLM。
- 不引入 Agent Loop 或多模型。
- 不修改 Planner、Validator、HITL、Engine 的业务逻辑。
- 不重新开发 Report Module。
- 不使用 LLM 自行执行计算。
- 不使用展示模板掩盖生成层的质量问题。

## 四、交付物

1. 修改文件清单。
2. 新旧 Prompt 对比。
3. Evidence Builder 新增证据类型。
4. 多证据 fact/finding 生成机制。
5. Fact Validator 的安全边界说明。
6. 统一 AnalysisReport 与 Presentation 的方案及结果。
7. 优化前后真实模型评测。
8. 独立未见案例评测。
9. 自动化回归测试。
10. 剩余 Bad Case 和验收建议。

完成后先提交实际评测结果，不要直接宣称 V1.1 已达到专业分析师水平。
