# InsightFlow — HITL V2 业务友好型分析方案审核页

## 产品目标

将现有面向开发者的技术计划审核页面，改造为面向普通业务人员的分析方案确认页面。

核心原则：让用户理解 AI 将分析什么、使用什么范围与口径、从哪些方向分析、哪些问题需要确认。

## 页面信息架构

按照以下顺序展示：

1. 核心分析目标：用一句简洁业务语言说明本次分析要解决什么问题。
2. 分析范围与统计口径：时间、筛选范围、指标、维度、排序、Top N、排除条件。
3. 分析方向：按业务问题展示每个任务，区分核心分析、辅助分析、补充分析。
4. 待确认事项：只展示真实影响审批或分析结果的问题，并说明下一步如何解决。
5. 确认与操作：确认并开始分析、删除非必要任务、查看详情。

## 展示规则

- 默认不展示字段 ID、Schema、Hash、操作参数、F0/F1/F2 原始枚举或技术错误码。
- 优先级 P0/P1/P2 转换为业务语言。
- 将技术可执行性转换为用户可理解的状态，但不得隐藏实际阻断。
- 复杂技术信息放入可展开的“技术详情”。
- 不展示未经真实计算的数值结论。
- 不承诺尚未实现的报告图表能力。
- 不能为了让页面好看而虚构分析方向或补全未确认的统计口径。

## 数据实现

优先新增独立的 Plan Presentation Mapper / Review ViewModel。

复用现有 IntentResult、AnalysisPlan、ValidatedAnalysisPlan。

保持原审批、计划版本和执行契约不变。

所有展示字段必须能追溯到已有业务字段或验证结果。

不得额外调用 LLM 生成展示内容。

## 审批阻断处理

当前系统存在“约束未经结构化验证”的审批阻断。

请先审计现有 Validator 和审批规则，明确每条约束的来源、目标字段、实际操作步骤、校验结果。

设计确定性的约束映射审计：

- 已映射且验证通过：允许作为审批依据。
- 未映射或语义不明确：保留阻断并解释原因。
- 缺少字段或不支持能力：展示真实缺口。
- 需要用户补充口径：提示确认，不得自动假设。

不得通过隐藏警告、删除约束或直接放宽审批条件解决。

## 交互要求

- 用户可以查看每个分析方向的业务问题。
- 可以删除非必要任务并重新校验。
- 可以查看分析条件和待解决问题。
- 批准按钮必须严格绑定服务端审批资格。
- 不要添加无法工作的自然语言修改按钮。
- 如果需要修改范围但尚未实现修订能力，应明确提供重新提出需求的入口。

## 验收

至少使用销售订单、招聘、客服工单、项目任务四类场景测试。

重点检查：

1. 普通用户能否快速理解核心目标。
2. 分析方向是否与实际计划一致。
3. 时间、范围、指标、排序是否完整展示。
4. P0/F0 等风险是否正确转换为业务提示。
5. 技术详情是否与真实计划一致。
6. 未验证约束不能被误认为已验证。
7. 不得绕过真实 HITL 审批。
8. 版本变化、任务删除和刷新恢复后，展示仍与当前计划一致。
