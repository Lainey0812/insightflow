# InsightFlow — Insight Generator V1.1 洞察质量优化任务书

## 一、任务背景

InsightFlow 已经实现：

用户自然语言需求 → Analysis Planner → HITL → Analysis Engine → Report Module。

目前 Report Module 已经能够生成真实的分析报告，包含关键指标、图表、核心发现、业务建议和证据追溯。

但实际报告的洞察质量仍然较低。

以销售订单测试为例：

**用户需求：**

分析 2026 年华东地区已完成订单的销售额，按照城市汇总并降序排名，取前三名。

**实际计算结果：**

| 城市 | 销售额    |
| -- | ------ |
| 济南 | 21,250 |
| 南京 | 20,250 |
| 上海 | 5,760  |

Evidence Builder 已经产生：

- 济南销售额 21,250，排名第一。
- 南京销售额 20,250，排名第二。
- 上海销售额 5,760，排名第三。
- 济南领先南京 1,000。
- 前三名城市销售额合计 47,260。

但最终报告只生成了一条主要洞察：

“济南的已计算指标值为 21,250。”

业务解释：

“该分组在当前筛选范围内销售额表现突出，可作为进一步核查业务表现的切入点。”

存在的问题：

1. 洞察只是复述原始统计结果。
2. 没有充分利用排名、差异和汇总证据。
3. 没有形成具有业务意义的比较结论。
4. 建议较为通用，没有针对实际发现。
5. 报告标题及部分文字偏向技术描述，不适合普通业务人员。

## 二、本轮目标

优化 Insight Generator 的业务分析质量，使其能够：

1. 从多个证据中识别值得关注的业务发现。
2. 对数据进行有依据的比较与解释。
3. 说明发现可能对业务判断产生什么影响。
4. 提出与发现直接相关、可验证的下一步分析建议。
5. 保证所有数值和事实均可追溯。

本轮不要求生成更多文字，而是提高每条洞察的信息价值。

## 三、第一阶段：定位问题

在修改代码和 Prompt 之前，先审计现有 Report Module。

请回答：

1. Evidence Builder 当前输出了哪些证据？
2. 哪些证据被传入 Insight Generator？
3. Insight Generator 使用什么 Prompt？
4. LLM 实际返回了哪些候选洞察？
5. 是否存在洞察筛选、排序、截断、去重或校验逻辑？
6. 哪些洞察最终进入 AnalysisReport？
7. 有没有固定的洞察数量限制？
8. 当前业务建议是 LLM 生成还是规则模板生成？
9. 是否存在真实 LLM 调用失败后使用模板兜底的情况？

请提供：

Evidence → LLM 输入 → LLM 原始输出 → 后处理 → 最终报告

的完整链路。

**先定位质量损失发生在哪一层，不要直接修改 Prompt。**

## 四、第二阶段：优化洞察生成能力

### 1. 证据优先级

不要平均使用所有证据。

优先识别与用户目标最相关的证据，例如：

- 排名与领先关系。
- 组间差异。
- 占比与集中程度。
- 时间趋势及变化。
- 异常值与明显偏离。
- 用户明确关注的指标。

注意：只有当 Evidence Builder 实际提供了相应证据时才能使用。

不要为提高洞察数量而强行生成不存在的趋势或异常。

### 2. 多证据综合分析

鼓励将多个相关证据组合成一个完整的业务发现。

例如：

证据 A：济南销售额 21,250。

证据 B：南京销售额 20,250。

证据 C：两者相差 1,000。

优质洞察：

“济南排名第一，但与南京的销售额较为接近，两者仅相差 1,000。”

如果需要使用 4.9% 等新计算指标，必须先由确定性 Evidence Builder 计算并提供对应证据，不能让 LLM 自行生成未经验证的数值。

### 3. 洞察结构

建议每条 Insight 包含以下逻辑内容：

**Finding：事实发现**

数据实际发生了什么？

**Business Implication：业务含义**

这一发现为什么值得用户关注？

**Recommendation：下一步建议**

基于现有证据，用户还应该分析或确认什么？

**Evidence References：证据引用**

该洞察依赖哪些实际计算结果？

优先复用现有 Insight Schema。

如果现有 Schema 已经能够表达这些信息，不要新增字段。

### 4. 业务解释边界

允许：

- 描述已验证的排名。
- 比较真实的组间差异。
- 识别有证据支持的变化。
- 提出需要进一步验证的业务假设。
- 指出当前数据无法解释的问题。

禁止：

- 编造不存在的销售额或比例。
- 将相关性直接解释为因果关系。
- 将排名靠后直接解释为经营失败。
- 在没有利润数据时判断盈利能力。
- 在没有营销数据时判断营销策略效果。
- 将 Top N 结果误当作完整总体。

### 5. 洞察数量

根据证据的实际信息量决定。

默认可生成 1–3 条高价值洞察，但不强制凑数。

一条有意义的洞察优于三条重复的描述。

### 6. 建议质量

每条建议必须与某条发现建立明确联系。

建议应尽量具体、可验证。

例如：

不推荐：

“建议进一步优化销售策略。”

推荐：

“建议进一步比较济南、南京和上海的订单数量及平均订单金额，判断销售额差异与订单规模或客单价的关系。”

不能将尚未执行的分析写成已完成结论。

## 五、第三阶段：优化生成策略

请基于实际问题选择最小有效方案。

优先考虑：

1. 调整 Evidence 的组织和输入顺序。
2. 在 Prompt 中明确洞察筛选与比较规则。
3. 改进重复洞察过滤。
4. 改进证据引用校验。
5. 改进业务建议与发现的关联。

不预设一定需要多个 LLM、Agent Loop 或多轮反思。

优先沿用当前单 LLM 架构。

不要在本轮修改 Analysis Planner、Validator、HITL 或 Analysis Engine。

## 六、第四阶段：建立洞察质量评测

至少使用以下数据场景：

- 销售订单。
- 招聘信息。
- 客服工单。
- 项目任务或运营数据。

评测维度：

### A. 事实准确性

是否存在虚构数值、错误排名或错误统计口径？

### B. 证据利用

是否合理使用与用户目标相关的重要证据？

### C. 洞察深度

是否超越简单数值复述，形成比较、变化或结构性发现？

### D. 业务相关性

是否直接回答用户原始分析目标？

### E. 建议可执行性

建议是否具体，并与已有发现相关？

### F. 表达质量

是否使用普通业务人员能够理解的语言？

### G. 安全边界

是否存在因果过度推断、Top N 总体误读或缺少数据支持的判断？

每个维度需要有明确评分标准。

保留优化前后的相同输入、模型输出、最终报告和评分结果。

另准备独立未见测试案例，不能只针对销售订单数据调优。

## 七、验收要求

必须满足：

- 数值事实与 Evidence 一致。
- 每条核心洞察有有效 evidence_refs。
- 不存在未经验证的新增计算结果。
- 不存在无依据的因果解释。
- 不存在 Top N 被误解为总体的情况。
- 优化后洞察业务价值相较基线有可解释的提升。
- 原有 Report Module、Workflow 和 Engine 测试不退化。

业务质量提升必须由实际案例及评分支持，不能仅凭 Prompt 变长或报告文字增多判断成功。

1. 当前 Insight Generator 实现审计。
2. 质量问题根因。
3. 修改文件清单。
4. 新旧 Prompt 对比。

6. 优化前后洞察对比。
7. 多领域评测结果。
8. 真实 LLM 调用记录。
9. 剩余 Bad Case。
10. 是否建议进入下一阶段报告 UI 优化。
