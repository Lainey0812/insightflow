# InsightFlow Admin：工作流节点详情统一完善需求

## 一、任务目标

请基于 InsightFlow 现有代码，完善 Admin 运行追踪页面中各工作流节点的详情展示能力。

目前 Admin 已采用左右双栏布局：

- 左侧：展示完整 Workflow 执行链路，包括节点名称、状态、耗时和异常标识。
- 右侧：根据左侧选中的节点，展示该节点本次执行的输入、输出和模型调用信息。

本次任务不重新设计页面布局，而是完善每个节点的业务信息展示，使管理员能够通过查看节点输入、输出及上下游关系，定位分析结果偏差、执行异常和数据质量问题。

核心目标是：**能够看清每个节点接收了什么、做出了什么判断、输出了什么，以及该输出是否符合上游输入和下游契约。**

## 二、开发前必须检查现有实现

先检查 InsightFlow 的工作流定义、节点实现、数据契约、运行记录、持久化结构和 Admin 组件。

必须确认：

1. 实际存在哪些节点及其执行顺序，是否存在条件分支、循环、重试或跳过。
2. 每个节点的真实 Input / Output Schema。
3. 哪些节点实际调用 LLM，哪些是确定性执行或人工交互节点。
4. 每个节点的输入输出是否已持久化，以及历史记录的可用范围。
5. 节点与 Workflow、Run、Node Run、LLM Call 的真实关联关系。
6. 当前 Admin 已实现哪些展示能力。

输出字段差距清单，区分「已有且已展示」「已有但未展示」「执行时存在但未持久化」「完全缺失」「不适用」。

**以下字段均为期望展示的语义信息，不要求强行采用文档中的英文命名。实际开发应以项目现有 Schema 为准。**

不允许为了 Admin 展示而大规模修改工作流业务契约。

---

## 三、所有节点的统一展示规范

### 3.1 顶部节点概览

右侧顶部固定展示：

- 节点名称及实际 Node Run ID。
- 执行状态：成功、失败、运行中、等待、跳过、未执行等。
- 开始时间、结束时间和执行耗时。
- 已记录的错误代码或异常提示（如果存在）。
- 已记录的质量信号数量（如果存在）。

节点成功时不需要显示独立的错误诊断区域。

节点失败时，在顶部展示简要错误说明，允许展开查看完整错误信息。

### 3.2 Tab 规则

实际调用 LLM 的节点，使用 Input / Output / LLM 三个 Tab。

不调用 LLM 的节点，使用 Input / Output 两个 Tab。

对于同一个节点类型存在不同执行模式的情况，应根据实际 Node Run 是否具有 LLM Call 来决定是否展示 LLM Tab，而不是仅依靠节点名称判断。

不新增 Diagnostics Tab。

### 3.3 Input 展示规则

Input 只展示本次节点实际接收到的业务数据、上游输出和执行参数。

不能把当前数据库中的最新数据冒充历史输入。

### 3.4 Output 展示规则

Output 优先使用业务化组件展示结构化结果，同时支持查看实际保存的原始 Output JSON。

如果存在错误、警告、待确认事项，应在对应业务区域展示，而不是全部集中到独立诊断页面。

### 3.5 LLM 展示规则

统一复用现有模型调用组件，展示：

- Call ID、模型名称、Prompt 模板和版本。
- 调用状态、耗时和 Token。
- 实际记录的模型参数。
- 已保留的请求和响应。
- 调用失败信息。
- 重试或多次调用记录。

支持跳转 Prompt 管理页面。

如果请求或响应未保留、已过期或不可访问，应明确显示对应状态，不重新调用模型补写历史。

# 四、Analysis Planner：分析规划节点

## 4.1 Input

展示实际传入的结构化需求和数据画像：

- 分析模式：目标驱动型或探索型。
- 用户分析对象和业务目标。
- 显式约束、排除条件和筛选范围。
- 尚未解决的澄清事项。
- 数据集标识。
- 数据字段名称、类型及可用性。
- 数据质量信号。
- 实际生效的规划配置和规则。

Input 重点是让管理员确认 Planner 是否获得了正确、完整的需求与数据上下文。

## 4.2 Output

展示生成的分析计划。

**计划概览**

展示分析目标、计划摘要、任务总数、核心任务数量、补充任务数量及计划生成状态。

**分析任务列表**

每个任务采用可展开卡片，展示：

- 任务 ID、任务名称和分析目标。
- 核心任务或补充任务。
- 业务价值分级及其依据（如果有）。
- 数据可行性分级及其依据（如果有）。
- 需要使用的数据字段。
- 分析维度、指标和拟采用的方法。
- 必须遵守的用户约束。
- 任务依赖、风险和待确认条件。
- 实际存在的其他规划参数。

**规划风险**

展示 Planner 已识别的字段缺失、数据能力不足、业务口径歧义、假设和不可行任务。

保留原始 AnalysisPlan JSON 查看能力。

注意：Planner 输出的可行性是规划判断，不代表 Plan Validator 已经验证通过，也不代表用户已经批准计划。

## 4.3 LLM

关联该节点的实际模型调用，复用统一 LLM 组件。

# 五、Plan Validator：计划校验节点

## 5.1 节点职责

Plan Validator 负责检查分析计划是否满足已定义的结构与执行硬约束。

重点是判断计划能否合法进入后续流程，而不是重新评价任务的业务价值。

## 5.2 Input

展示：

- 待校验计划 ID 或版本。
- 实际提交校验的完整计划结构。
- 数据集标识及 Schema。
- 允许的任务类型、操作符和计算方法。
- 已配置的字段引用、类型、依赖关系等校验规则。
- 其他实际传入的校验上下文。

## 5.3 Output

**校验结果概览**

展示通过、失败或其他实际校验状态，校验规则数量、通过数量、失败数量及阻断项数量（如果有记录）。

**校验问题列表**

每个问题展示：

- 规则代码。
- 严重程度。
- 关联任务 ID。
- 关联字段或 JSON 路径。
- 失败原因。
- 期望条件。
- 实际检测值。
- 是否阻断。
- 实际存在的修复建议。

支持按任务 ID、规则代码和严重程度筛选。

**校验后的计划**

如果 Validator 会返回标准化计划、修正建议或校验报告，应展示真实结果。

如果 Validator 只返回通过/失败和错误列表，不要虚构修正后的计划。

保留原始校验结果 JSON。

## 5.4 边界

Validator 不负责重新生成计划，不得未经用户确认自动修改业务分析目标。

如果现有 Validator 不调用 LLM，仅显示 Input / Output。

---

# 六、HITL：用户计划审批节点

## 6.1 节点职责

HITL 负责记录用户对分析计划的确认、拒绝或修改行为，确保后续执行建立在用户已确认的计划之上。

它不负责判断分析计划是否具有业务价值，也不负责执行计算。

## 6.2 Input

展示：

- 提交审批的计划 ID、版本或内容摘要。
- 实际展示给用户的计划快照。
- Validator 校验结果（如果作为输入）。
- 需要用户确认的假设、口径或风险。
- 审批请求创建时间。
- 实际存在的其他审批上下文。

## 6.3 Output

**审批状态**

展示等待审批、已批准、已拒绝、已取消或其他实际支持的状态。

**用户决策**

展示：

- 决策类型。
- 决策时间。
- 用户修改内容或拒绝原因（如果有）。
- 修改前后的计划差异（如果存在真实版本）。
- 最终批准的计划 ID、版本或快照引用。
- 后续工作流实际采用的计划引用。

如果用户修改计划后需要重新校验和审批，应展示实际发生的状态流转及关联记录。

**审批历史**

以时间线展示真实的提交、修改、拒绝、重新提交和批准事件。

如果当前后端只保存最终状态，先标记历史不可用，不虚构审批过程。

## 6.4 边界

Admin 仅查看历史审批记录，不允许管理员从运行追踪页面代替用户批准、拒绝或修改计划。

必须区分：

- 用户批准了什么计划。
- 系统最终执行了什么计划。

如果现有系统具备计划版本绑定、哈希或快照机制，应展示相应标识，方便核对两者是否一致。

HITL 默认只使用 Input / Output，不需要 LLM Tab，除非实际执行记录包含模型调用。

---

# 七、Analysis Engine：分析执行节点

## 7.1 节点职责

Analysis Engine 负责根据已经确认且通过校验的执行规格，完成数据过滤、分组、聚合、统计和其他已支持的确定性计算。

该节点最重要的检查目标是：

**实际执行是否符合批准的计划，计算结果是否可以追溯到明确的数据和计算规则。**

## 7.2 Input

展示：

- Dataset ID 和实际使用的数据版本或快照引用。
- 已批准的计划 ID、版本或哈希（若存在）。
- 实际执行规格 ExecutionSpec。
- 任务 ID 和执行顺序。
- 使用的数据字段。
- 过滤条件。
- 分组维度。
- 聚合指标与计算规则。
- 排序、限制、空值处理等实际生效的执行参数。
- 任务依赖关系。

对于多个分析任务，采用任务列表或分组卡片展示，不要将所有执行规格混成一个大 JSON。

## 7.3 Output

**执行概览**

展示执行状态、任务总数、成功任务数、失败任务数及总耗时。

**任务执行结果**

每个任务展示：

- 任务 ID 和名称。
- 执行状态与耗时。
- 实际使用的计算规则。
- 输入记录数。
- 过滤后有效记录数。
- 输出结果类型。
- 结果摘要。
- 结果数据引用。
- 错误代码和错误说明（如果失败）。

仅展示后端实际记录的行数和指标。

**计算依据**

如果当前系统保存了计算依据，展示来源数据、筛选条件、有效样本数、计算公式及结果之间的关联。

对于大型明细数据，优先展示摘要和已有的分页查询或结果引用，不在 Admin 中直接渲染完整数据集。

**任务失败**

如果某个任务失败但其他任务成功，应按实际执行策略展示部分成功状态，不要直接将所有任务都标记为失败。

保留 ExecutionResult JSON 查看能力。

## 7.4 边界

Admin 不重新执行计算，不修改已保存的计算结果。

不要为了展示计算依据而重新生成一个可能与历史结果不同的数字。

如果当前系统只保存最终结果，没有保存足够的计算依据，应明确标记证据不完整，并评估是否需要为后续运行增加必要的执行摘要。

Analysis Engine 默认仅显示 Input / Output。

---

# 八、Insight Generator：洞察与报告生成节点

## 8.1 节点职责

Insight Generator 根据 Analysis Engine 的真实计算结果生成自然语言洞察、图表说明和分析报告。

重点是判断：

- 生成内容是否基于真实计算结果。
- 关键结论是否存在对应数据依据。
- 是否出现无依据的数字、结论或过度推断。

## 8.2 Input

展示：

- 分析目标及用户约束。
- 已批准计划或相关任务摘要。
- Analysis Engine 的实际执行结果。
- 关键指标和计算结果。
- 结果数据引用。
- 已有的数据质量提示。
- 实际使用的报告生成配置。

重点展示模型实际获得了哪些计算结果，不能把没有传入模型的字段当成其输入。

## 8.3 Output

**报告概览**

展示报告 ID、生成状态、标题、生成时间及实际存在的报告版本。

**报告内容**

按照真实输出结构展示：

- 核心结论。
- 关键发现。
- 指标说明。
- 图表或图表配置。
- 业务解释和建议（如果存在）。
- 数据限制及注意事项。

**结论与依据**

如果系统已有结论级证据引用，应展示每条关键结论关联的任务 ID、指标、计算结果或数据引用。

如果当前只实现 Workflow 级追溯，没有结论级证据关联，不得声称每条结论都已经完成溯源。

可以展示已有的来源信息，并明确标记尚未建立结论级关联。

**质量信号**

展示已检测到的数值不一致、无依据结论、引用缺失、结构化输出错误等信号。

不能仅因为报告生成成功就标记内容质量合格。

支持查看原始结构化 Output JSON 和已有的报告详情。

## 8.4 LLM

展示实际报告生成模型调用，包括 Prompt 版本、模型配置、请求、响应、Token、延迟和错误信息。

## 8.5 边界

Admin 不自动改写历史报告，不重新生成结论，不补造证据引用。

报告质量判断需要独立证据，不能直接采用模型自己的自我评价作为已验证结论。

---

# 九、其他实际存在的节点

如果工作流中还存在 Intent Clarifier、Plan Revision、ExecutionSpec Builder、Report Persistence 或其他节点，不得忽略。

请先根据实际代码确认它们的职责，再按照以下原则补充：

- Input 展示实际接收的数据、版本和配置。
- Output 展示真实业务结果、状态及关联标识。
- LLM Tab 仅在真实存在模型调用时显示。
- 业务状态和错误信息按实际记录展示。
- 不擅自改变节点职责或输出契约。

对于数据持久化节点，应重点展示写入目标、关联 ID、写入状态及实际错误；对于计划修改节点，应重点展示修改前后差异和版本关系。

不要为不存在的节点创建占位页面。

---

# 十、跨节点质量检查重点

Admin 的目标不仅是查看每个节点自身是否成功，还需要帮助管理员发现上下游不一致。

重点保留以下关联关系：

**Intent Parser → Analysis Planner**

检查 Planner 是否保留用户目标与显式约束。

**Analysis Planner → Plan Validator**

检查生成的计划是否满足 Schema、字段和执行规则。

**Plan Validator → HITL**

检查提交用户审批的是否为预期计划版本。

**HITL → Analysis Engine**

检查实际执行规格是否对应用户已批准的计划。

**Analysis Engine → Insight Generator**

检查报告使用的指标和结果是否来自真实计算输出。

这些关系优先通过节点间的 ID、版本、快照及已有 Trace 信息展示。

本次不要求新增自动跨节点质量判定引擎。

---

# 十一、前端统一交互要求

1. 保留现有左侧完整 Workflow、右侧节点详情布局。
2. 点击左侧节点后，右侧展示该次 Node Run 的真实信息。
3. LLM 节点采用 Input / Output / LLM，非 LLM 节点采用 Input / Output。
4. 每个 Tab 内优先使用业务化展示组件，不直接将整个 JSON 作为唯一界面。
5. 所有节点保留已有结构化 JSON 查看能力。
6. 支持复制实际保存的 JSON。
7. 任务列表、校验问题、计算结果和质量信号应使用可展开列表或表格。
8. 需要区分未执行、无输出、未采集、已过期和接口加载失败。
9. 左侧节点切换时，不得串用其他 Node Run 的数据。
10. 右侧只读，不允许修改历史输入输出。
11. 对存在多次尝试或重试的节点，必须明确当前展示的是哪次执行。
12. 尽量复用现有组件和样式，避免重复建设相似页面。

---

# 十二、数据补齐与后端约束

字段已经存在但未展示：直接复用。

字段执行时存在但未持久化：评估必要性，在现有 Trace 或 Node Run 记录中补充。

字段完全不存在：先判断是否属于节点职责和当前 MVP 必需信息，再决定是否新增。

优先补充可观测性元数据，不轻易修改业务 Input / Output Schema。

不得为了 Admin 展示而改变 Analysis Planner、Validator、HITL、Engine 或 Insight Generator 的现有业务行为。

所有新增字段应兼容旧记录。

旧记录缺少的数据展示为未采集，不能通过重新运行节点伪装成历史结果。

不得复制保存原始上传文件或绕过现有数据访问控制。

---

# 十三、验收要求

使用真实 Workflow 或明确标识的测试运行，验证以下场景：

1. Planner 能展示实际需求、数据画像和分析任务。
2. Validator 能展示真实校验输入、规则结果和失败原因。
3. HITL 能展示提交审批的计划及真实用户决策。
4. Engine 能展示批准计划、执行规格、任务状态和计算结果。
5. Insight Generator 能展示计算输入、报告输出和真实模型调用。
6. LLM 节点能够查看真实 Prompt 版本和调用记录。
7. 历史记录缺失字段时能够正确显示未采集。
8. 节点切换、重试和失败场景不会发生数据错位。
9. 现有 Workflow 执行、审批、计算和报告流程保持正常。
10. 新增的 Admin 详情不会修改任何历史执行数据。

完成后运行项目已有的类型检查、构建和相关测试。

---

# 十四、执行顺序与交付

请分阶段执行：

**阶段一：现状审计**

输出实际节点清单、真实 Input / Output Schema、LLM 调用情况、现有 Admin 展示能力和缺失字段。

**阶段二：最小改动方案**

明确前端组件、后端接口、持久化结构及兼容性风险。

**阶段三：实施**

优先完善现有字段的展示，再补充必要的 Trace 采集与持久化。不要为非核心统计字段扩大开发范围。

**阶段四：验证**

使用真实运行记录或明确标识的测试数据验证各节点的输入输出和跨节点关联。

**阶段五：交付报告**
