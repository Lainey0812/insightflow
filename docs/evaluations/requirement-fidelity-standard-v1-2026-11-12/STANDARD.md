# 需求保真评测标准 v1

日期：2026-11-12。需求：REQ-0138，关联 REQ-0137。本文件只定义标准和用例，不修改产品代码，也不改 REQ-0137 已有评分。

评测回答一个问题：用户原始需求里的目标和约束，有没有被最终计算真正执行。计划版本一致、步骤编号跑过、报告可以回溯，都不能单独算通过。

## 结论怎么下

用例结论只有四种：通过、失败、阻断、用例无效。

通过只有一条规则：端到端结果与独立基准一致，并且和拿掉该约束后的对照基准不一致。对照基准必须事先手算，不能从本次模型输出反推。

节点诊断永远记录，但不单独决定结论。端到端失败时，诊断指出第一处丢失。端到端通过时，诊断里的缺口仍保留，不能把用例改判失败，也不能把「计划里写了排除」写成通过。

模型不可用、或原话确实不足以执行而停在澄清，记阻断。数据集里本来没有被排除的取值，记用例无效，不能记通过。

## 三个环节

Intent Parser 检查三件事：分析目标、纳入条件、排除条件。目标要能看出比较对象和指标。纳入条件和排除条件要进入结构化约束，方向不能反。`不排除` 不是排除。`只看` 不是排除。`不要求` 不是禁止。

Analysis Planner 检查这些条件有没有进到具体任务。受影响的汇总任务必须在聚合前带上对应筛选。分组、指标和方向要与原话一致。只写进任务标题、没有进步骤，不算继承。

Analysis Engine 检查实际算出来的表。执行日志里的步骤编号和行数变化只作诊断。过滤谓词不在步骤日志里，所以不能用「有一条 filter 步骤」证明排除已经生效。

Plan Validator 不单列成第四个验收门。批准计划把规划里的条件弄丢时，诊断记在规划与执行之间，用例仍然按端到端结果下结论。

## 端到端怎么判排除

用户说「对比上海和深圳的岗位数量，排除实习岗位」时，结果按城市给出数量。实习是行过滤，不是结果里的分组名。结果单元格里没有「实习」两个字，不能证明排除已执行。

必须同时满足：

1. 结果等于正确基准。正确基准先去掉实习，再只保留上海和深圳，按行计岗位数。
2. 结果不等于未排除基准。未排除基准仍只保留上海和深圳，但实习行也计入。
3. 两组基准的数字必须不同。没有不同，这条用例无效。

结果等于未排除基准，失败类型是排除未生效。结果等于只保留实习的基准，失败类型是方向反了。结果多出北京或其他城市，失败类型是纳入范围丢失。上海的岗位数等于岗位名称去重数、而不等于行数时，失败类型是指标被替换。只有一个总数、没有两个城市，失败类型是目标被替换。

## 失败类型

端到端失败用下面七类，一类对应一种对照基准。对不上任何对照基准时用最后一类，不勉强归类。

| 代码 | 含义 | 判定 |
| --- | --- | --- |
| F-EXCLUDE-DROPPED | 排除没有进入计算 | 结果等于未排除基准，或被排除分组仍在且数量与未排除基准相同 |
| F-POLARITY-REVERSED | 排除做成了只保留 | 结果等于「只看被排除取值」的基准 |
| F-INCLUDE-DROPPED | 纳入范围丢失 | 少了应比较的城市，或多出范围外的城市 |
| F-METRIC-SUBSTITUTED | 指标被替换 | 结果等于另一种口径的基准，例如岗位名称去重、薪资解析 |
| F-GOAL-SUBSTITUTED | 回答了另一个问题 | 没有要求的分组，只给总数，或主结果不是岗位数量 |
| F-EXTRA-CONSTRAINT | 多加了用户没说的条件 | 结果等于更窄的对照基准 |
| F-ORACLE-MISS | 计算偏离全部分对照 | 与正确基准和上述对照都不相等 |

节点诊断用下面这些代码。它们解释失败，或在通过时留下记录。

| 代码 | 环节 | 含义 |
| --- | --- | --- |
| D-INTENT-MISSED | Intent | 目标、纳入或排除没有进入结构化约束 |
| D-INTENT-PROSE-ONLY | Intent | 条件只出现在目标正文 |
| D-INTENT-REVERSED | Intent | 排除被写成只看，或只看被写成排除 |
| D-PLAN-MISSING | Planner | 汇总任务在聚合前没有对应筛选、分组或指标 |
| D-PLAN-PARTIAL | Planner | 只有部分汇总任务带上了条件 |
| D-PLAN-REVERSED | Planner | 步骤方向与原话相反 |
| D-PLAN-TEXT-ONLY | Planner | 条件只在任务标题或问题里，步骤没有 |
| D-BETWEEN-PLAN-ENGINE | 规划与执行之间 | 规划结果有该条件，实际执行的计划没有 |
| D-ENGINE-STEP-ABSENT | Engine | 执行计划有该步骤，日志里没有成功跑过 |
| D-ENGINE-RESULT-DIVERGE | Engine | 步骤在，结果仍与正确基准不一致 |

第一处丢失按 Intent、Planner、执行计划、Engine 这个顺序取。后面的环节即使也错，不改第一处。端到端通过时这些代码记为观察，不改结论。

## 用例设计规则

每条排除用例的数据里，被排除取值必须真实存在，并且拿掉它以后数字会变。纳入范围外的行也必须存在，用来发现多算进来的城市。

行数和岗位名称去重数必须不同，否则发现不了「岗位数量」被换成去重。现有 `recruitment.csv` 没有实习行，也没有岗位类型列，不能充当这组用例。下面的表是专供本标准的合成数据，还不是产品里的文件。

| 编号 | 城市 | 岗位名称 | 岗位类型 |

| J02 | 上海 | 产品经理 | 正式 |

| J04 | 上海 | 产品经理 | 实习 |
| J05 | 深圳 | 产品经理 | 正式 |

## 用例

### RF-01 主用例

原话：对比上海和深圳的岗位数量，排除实习岗位。

正确基准：上海 3，深圳 1。未排除基准：上海 4，深圳 3。只看实习：上海 1，深圳 2。名称去重且排除实习：上海 2，深圳 1。不限城市且排除实习：上海 3，深圳 1，北京 1。

通过：结果正好是上海 3、深圳 1。这个结果不等于未排除基准，所以排除生效。

失败对照：等于上海 4、深圳 3，是 F-EXCLUDE-DROPPED。等于上海 1、深圳 2，是 F-POLARITY-REVERSED。出现北京或杭州，是 F-INCLUDE-DROPPED。等于上海 2、深圳 1，是 F-METRIC-SUBSTITUTED。只有总数 4，是 F-GOAL-SUBSTITUTED。

### RF-02 不要把「不排除」做成排除

原话：对比上海和深圳的岗位数量，不排除实习岗位。

正确基准：上海 4，深圳 3。若结果变成上海 3、深圳 1，是 F-EXTRA-CONSTRAINT。Intent 若把「不排除实习」收成排除，诊断为 D-INTENT-REVERSED。

### RF-03 只看不是排除

原话：只统计实习岗位，对比上海和深圳的岗位数量。

正确基准：上海 1，深圳 2。若结果变成上海 3、深圳 1，是 F-POLARITY-REVERSED。

### RF-04 指标边界

原话：对比上海和深圳的岗位数量，排除实习岗位，不要分析薪资。

端到端基准与 RF-01 相同。主结果仍是上海 3、深圳 1 时，用例通过。另有薪资任务但没有取代这个结果时，只记诊断，不改通过。没有岗位数量、只剩薪资或无法执行的薪资任务，是 F-METRIC-SUBSTITUTED 或 F-GOAL-SUBSTITUTED。

### RF-05 被排除取值本身是分组

原话：按城市统计岗位数量，排除上海。

正确基准：深圳 3，北京 1，杭州 1。未排除基准：上海 4，深圳 3，北京 1，杭州 1。

通过仍看完整基准，不看「结果里有没有上海」这一句。上海还在且数量是 4，是 F-EXCLUDE-DROPPED。上海消失但杭州也消失，对照基准对不上，是 F-ORACLE-MISS，不算通过。

## 和上一版评分的边界

REQ-0137 的评分仍然保留。它不是这一版的验收结论。上一版对年份和纳入条件可以把「步骤跑过」记成引擎通过，对排除条件会检查结果单元格里有没有被排除的词。RF-01 的实习不会出现在城市数量表里，那种检查证明不了排除已执行。本标准以上面的对照基准为准。
