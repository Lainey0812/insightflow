## 当前结论

最新 v1.2.3 的已知短语安全补丁没有解决自由解释的普遍可靠性问题。24例的模型调用正常、实际计算一致，但仍有无依据业务解释进入报告。**不通过 MVP 业务验收，不扩大目标用户试用。**

下一步建议修改内部 Report Draft 的职责契约，约束模型只能选择证据和有字段依据的后续方向，而不是继续通过正则追逐所有自然表达。具体待评审方案见 [next-step-contract-proposal.md](next-step-contract-proposal.md)，本轮未实施该方案。

## 三类主要问题与证据

### 1. 无依据解释仍会绕过有限词语守卫

- S03：把订单量差异联系到市场覆盖、客户基数和需求频次，缺少客户、时间频次或市场覆盖证据。
- P03：使用“占比极低”，并列举任务复杂度、人员配置、估算标准解释，缺少阈值和相关支持材料。
- V01：出现“极低水平”和“市场渗透不足/数据覆盖限制”原因候选，没有相应证据。

这些并非已修补的“更强用户粘性”原句，但属于相近的语义风险。仅有“可能/待验证”前缀不能证明合理。当前事实与证据引用的结构检查继续有价值，但自由解释的语义边界未解决。

### 2. 合法事实/否定边界与字段职责冲突

- S02 的最高/最低结论有排名或极值引用，但写在 implication 中触发统计词守卫。程序本来已在 finding 中表达事实；模型重复事实造成拒绝。
- T03 的“当前数据仅反映均值对比，不足以判断造成差异的具体原因...”依然因“造成”触发；U04 的“目前数据不足以判断导致...”也有同类问题。
- P01 的“其中一个月份”触发数字守卫，引用中已有对应月份排名。但该候选还夹杂未充分支持的强度/原因表达，不能把整个候选直接放行。
- S01 的“绝大部分、主导作用”没有已验证阈值，拒绝合理，应让生成层选择可以证明的事实，而不是放宽守卫。

需要区分局部表达误判与候选整体合格，不能把所有拒绝都叫误拦截。

### 3. 建议没有绑定领域与真实字段

R03 是招聘岗位计数，最终建议却是“订单数量、平均订单金额、产品构成、销售差额”。引用合法不代表建议相关。后续建议应有真实字段和语义职责绑定，避免照搬 Prompt 示例。

## 审批拒绝与评测工具纠正

本轮 P02 的 Planner 输出了 `项目 ne 丙项目`，用户和 Gold 明确为 `项目 ne 丙`。因为丙没有已完成任务，两种条件在该样本上返回相同行集与数字。旧验收器自动把 goal_plan 记为true，审批层却正确拒绝。

本轮新加的是独立评测工具与六项测试，**不是修改业务审批**。它直接对照原冻结条件值，结果另存 [scope-literal-recheck.json](scope-literal-recheck.json)，保留原自动结果不动。20个明确目标计划中19个的受支持条件证明成立，P02不成立；不能把这个计数当作通用约束准确率。详见 [scope-audit-clarification.md](scope-audit-clarification.md)。

新增工具能识别冗余错误条件，即使计算结果碰巧相同，也不能据此宣称计划忠实。
