# MVP V1 基线：问题清单与修复顺序

以下为 2026-11-04 冻结样本的实际结果。本轮没有修改 Prompt、审批规则、分析算法或产品页面。问题优先级依据用户能否完成可信分析，而非模块开发顺序。

## BC-01：正确计划无法获得约束核验证明（P0）

影响 S02、R01、R03、R04、T02、T03、T04、P01、P02，共 9 例。

独立目标核验与计划计算预演均符合本例要求，但 `can_approve=false`。实际阻断包括：

- “订单数量”“岗位数量”“工单数量”“任务数量”没有映射到行计数。
- “只看一组和二组”无法对应已存在的 `in` 条件。
- “只统计已完成任务”“不包含丙项目”的短语与实际状态/排除步骤无法完成证明。
- “按月份升序”“降序取前两名”等表达未匹配现有有限语法。
- “不分析销售额”“不排除北京”和禁止推断原因的边界无法证明。

源码依据：`backend/app/review/constraint_audit.py:40` 的 metric 仅支持少量明确计数表达；`:55` 的 parse 与 `:130` 的 prove 采用有限语法，无法覆盖以上自然表达。`backend/app/services/plan_review.py:276` 的真实审批保持 fail-closed，不能靠勾选或隐藏提示解除。

定位：这是约束映射与证明能力不足，不是本批次模型把计划生成错，也不是 Engine 缺少计数能力。现有保守拒绝守住了安全边界，但业务可用性不合格。

修复建议：单独冻结明确支持的约束表达与结构化证明契约，逐项绑定真实字段/步骤。行计数必须与 sum(数量字段)、count(非空字段) 和 distinct_count 区分；多值范围、时间维度、否定边界分别处理。对无法证明的表达继续阻断。不得为提高成功率直接关闭约束审计，或把整段自然语言视为已确认。

## BC-02：否定边界和待验证解释被正则误拦截（P0 可用性）

S01 候选：“需进一步确认该差距是否由业务体量或统计口径导致。”T01 候选：“当前数据不足以判断导致该差异的具体原因或团队效率高低。”两者触发 FREE_TEXT_GUARD / UNSUPPORTED_ASSERTION，报告均变为 partial。

这是对原始候选的 agent_review：前者为待验证问题，后者明确限制因果推断，不等于已经证明原因。现有有限边界识别不覆盖这些表达。源码 `backend/app/reporting/fact_validation.py:196` 起对不同 role 的保护与匹配范围不一致。

修复建议：使用受控结构区分事实、边界与待验证建议，并对原始句子保持可追溯。保留肯定因果、经营判断、未经验证数值的拒绝；不能简单删除触发词或静默删改文本来制造完整成功。

## BC-03：探索报告遗漏 P0 证据（P0）

S03 的四任务全部计算成功；原始 LLM 只选择产品类别差异和时间变化，未覆盖“整体概况”“地区与城市差异”两个 P0 方向。触发 REPORT_CORE_FINDINGS_MISSING。执行结果保留，报告未交付。

源码：`backend/app/reporting/selection.py:2` 证据限量组织；`backend/app/reporting/fact_validation.py:315` 检查核心任务覆盖。现有拒绝是正确行为。

修复建议：先定义多任务情况下最低核心覆盖与证据预算，再调整证据组织/选择。不能删除 P0、降低覆盖要求，或把只含辅助发现的报告当作完整交付。

## BC-04：候选没有引用自身 primary evidence（P0）

P03 三个候选全部满足 JSON 外形，但每个 primary_evidence_id 均未出现在自己的 evidence_refs 中，全部被 REPORT_INVALID_EVIDENCE_REFERENCE 拒绝。原始输出与输入 Schema 都已保存。

源码：`backend/app/reporting/fact_validation.py:234`。现有拦截正确，不应放宽合法引用要求。

修复建议：确保生成契约明确主证据必须属于引用集合；考虑更少、更加受控的内部选择结构。若实施确定性补齐，必须先验证 ID 合法、同指标与范围兼容，并保持原始候选及修复记录；本轮未实施。

## BC-05：真实质量信息未绑定证据，导致单指标报告失败（P1）

P04 正确计算平均工时。LLM 在 limitations 中输出“上传范围内存在1条工时缺失记录，未纳入计算”，触发 NUMERIC。该缺失数与合成数据相符，但本候选仅引用 E0002（均值），没有相应结构化证据绑定，因此不能将其当作已验证事实直接放行。

修复建议：将必要的数据质量指标确定性转成可引用 Evidence，由受控事实表达渲染；不要允许 LLM 在自由文本自行补算或复述未绑定数值。不得以真实数据中恰好存在这个数字作为通用白名单。

## BC-06：较高响应时间被称为“领先”（P1 信任与可理解性）

T01 的 Presentation 使用“第一名响应分钟”“二组相对一组领先幅度”，对应二组均值 40 分钟。用户只要求比较响应分钟，没有定义越大越好。数值无误，但文案可能让业务用户理解为二组更优。

源码：`backend/app/services/analysis_report.py:235`、`:240` 对排名和 relative_lead 使用通用业务文案；新报告 Presentation 继承其保存指标。

修复建议：没有经过确认的指标方向时用“最高值”“高于幅度/差异”，不把数值排序解释为经营优劣。保留数值与证据，无须增加模型节点。

## BC-07：工程测试存在异步断言竞态（P2）

Admin 首次并行回归出现 1 failed / 87 passed：`src/tests/traces.test.tsx:105` 在 Inspector 事件请求 effect 执行前断言已调用。未改代码，独立重跑结果另存。不能覆盖首轮失败或将其归为产品真实模型问题。应另行以等待真实异步状态修复测试，不放宽业务断言。

## 下一阶段边界

先修 BC-01，使用相同冻结输入复测并增加新的独立表达；再修 BC-02–05 的报告交付问题，保留核心覆盖和事实安全要求。BC-06 是最小确定性展示修复，可随报告交付阶段处理。

在这些基础闭环稳定之前，暂缓 HITL 自然语言修订和真实用户扩大试用。用户试用协议已准备，但没有伪造招募或反馈。多 Workflow、Dashboard 与其他后台扩展不属于本轮。
